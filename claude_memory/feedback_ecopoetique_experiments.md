When iterating on a long-running classification pipeline (Task 0 narratology, Task 1 figurative classification, or similar multi-hour Ollama-based runs in [[project-ecopoetique]]):

1. **Always test a fix on a handful of items before relaunching the full run.** When `run_task0_v6.py` had a bug (qwen3 thinking mode not actually disabled, see [[project-task0-task1-status]]), the right move — confirmed working well — was: diagnose root cause via a direct API test, apply the fix, validate on the specific item that previously failed, THEN stop+archive the partial buggy run and relaunch clean. Don't patch-and-resume on top of a partial run generated under a different/buggy methodology — that mixes inconsistent generation processes in one results file.
2. **Confirm before stopping or restarting a multi-hour background run**, even though it's a low-stakes/reversible action — used `AskUserQuestion` before discarding partial v6 progress to apply the thinking-mode fix, and again before launching the expensive mapreduce_v6 experiment (~4h). She appreciated being asked rather than just acting, even though both runs are cheaply resumable.
3. **Don't over-interpret accuracy numbers from small samples.** Both v6 and mapreduce_v6 showed wild, misleading swings in the first ~15-35 novels before settling near their true value. State the running numbers but explicitly flag "too early to read into this" until the sample is large enough — she's been receptive to this caveat and it's prevented chasing noise.
4. **When asked for "an update," check actual process/file state directly** (ps, log tail, CSV row counts) rather than estimating from elapsed time — she asks for updates frequently during long runs and wants the real current state each time, not a projection.
5. **For autonomous "do X automatically while I'm asleep" requests**, prefer a plain detached OS-level background process (nohup, polling/sleeping) over an LLM-prompt-based scheduler (e.g. CronCreate) when the requirement is "must fire reliably with zero chance of me dropping the ball" — a cron job that re-invokes the agent depends on the session being idle/responsive at fire time, which is a weaker guarantee than a sleeping shell process. When asked for a backup/fallback trigger on top of an existing one, make it idempotent (check the target process isn't already running before launching) to avoid duplicate/conflicting runs.
6. **Watch for timezone mismatches in relative time requests.** She corrected an absolute "tomorrow 4am" interpretation that was actually wrong by several hours due to a UTC vs. her-local-time mismatch — when she gives a relative offset instead ("after 3.5 hours"), that sidesteps the ambiguity entirely and is more reliable than computing an absolute wall-clock target from the system clock.
7. **Before proposing a fix for a weak-accuracy criterion, empirically replay actual API calls on known-misclassified examples — don't just theorize from a confusion matrix.** She explicitly asked "check that these are the only issues... investigate first" after an initial 3-item fix plan (2026-07-01 daytime session, see [[project-task0-task1-status]]). Doing so surfaced a much bigger root cause (a context-truncation bug cutting visible text to ~10% of the novel) that the original plan would have completely missed, which would have wasted another multi-hour run on the wrong fix. Treat "investigate first" as a standing preference before any multi-hour rerun, not just when she says it explicitly.
8. **No gold-set examples or specific corpus novels in prompts.** She explicitly required this when approving the v7 narratology prompt rewrite — any per-chunk/reduce prompt text must stay purely definitional/generic (categories, rules, decision order), never reference a specific novel's plot, title, or gold label, to avoid overfitting the pipeline to the exact evaluation set. Applies to all future prompt-engineering work on this pipeline (Task 0 and Task 1 alike), not just the one fix she said it about.
9. **A small validation batch can hide a full-corpus regression — a "fixed" criterion needs the full run before it's trusted.** RÉGIME NARRATIF's fix looked like a clean win on a 15-novel sample (53%→66.7%) but regressed on the full 76-novel run (72.7%→63.2%) because the new rule overcorrected (over-triggering REG_AUTO on ordinary introspective first-person novels, not just genuine autofiction) — a failure mode the small sample happened not to expose. Don't declare a per-criterion fix "done" off a small batch alone if the full run is affordable soon after; treat the small batch as "safe to proceed to a full run," not as final confirmation. See [[project-task0-task1-status]] for the concrete numbers.
10. **When a per-chunk categorical judgment field keeps collapsing to one default answer, stop rewording it and change the architecture instead.** Three different wordings of an INTRIGUE per-chunk "is this fragmented" field (`narrative_unit_type`, `plot_threads`, `section_texture`) all independently collapsed to the "simple/coherent" default across every chunk tested, regardless of actual novel structure — confirming it wasn't a wording problem. What worked: drop the per-chunk categorical judgment entirely, keep only concrete factual extractions (who/what this section is about, a literal description of how it begins), and move the comparative judgment to the REDUCE step where the model can see all chunks at once. General principle for this pipeline: fields asking for FACTS reliably vary; fields asking for ABSTRACT CLASSIFICATION at the chunk level tend to collapse to the modal/majority answer, especially at temperature=0 with `format:json` forcing immediate token generation with no deliberation space.
11. **Verify "I found this in the transcript" claims from another session against the live files before trusting them — don't just accept a second opinion at face value.** Twice this session, another session's claimed quote/recollection of file contents (a classifier score, a `ROUTING` dict) turned out not to match what's actually on disk, including one claim that source files had been "erased" when they demonstrably still existed. Always re-derive from the live file (read it, or better, run the actual script) rather than accepting a transcript-search summary as ground truth — even when it's presented confidently and with specifics.
12. **Watch for leaky model selection, not just leaky training, when a script tries several models/methods and reports "the best one."** `train_chunk_classifier_60novels.py` tried 3 classifiers (LogReg/RF/GB) per criterion and reported whichever scored highest on the same leave-one-out loop being used as the reported score — that's picking a model using the test score itself, inflating results by +5.3pp overall (up to +13.4pp on ESPACE). Fix: nested CV (inner CV blind to the outer test fold picks the model type; outer CV only scores). This is a distinct failure mode from #9 (small-sample validation missing a regression) — it can happen even on the full eval set, any time "try N approaches, report the winner's score-on-the-same-set" is the pattern. Applies to any future scikit-learn/model-comparison script in this project, not just this one. See [[project-task0-task1-status]] for the concrete before/after numbers.
13. **When Labiba says "wait, I remember getting X" or corrects a number you reported, actually re-derive it from files rather than assuming she's misremembering.** She recalled TEMPORALITÉ hitting >70% when the current apples-to-apples eval showed 68.3% for v3 mapreduce — a broad scan of every result file with a TEMPORALITÉ column confirmed she was right (`resultats_hybrid.csv`/`hybrid_v4` genuinely score 71.7%, a real file-verified number). Her recollections of past numbers have been reliable ground truth to check against so far, not noise to wave away — treat them as a lead worth verifying, same weight as a fresh hypothesis.
14. **When a "frozen" result file's predictions differ from re-running its claimed source live, don't assume the drift is uniform (old-always-worse or live-always-worse) — check per-criterion.** Across all 7 narratology criteria, comparing `resultats_hybrid.csv`'s Jun-11 frozen predictions to the current live source files: 3 criteria improved live (TYPE, FOCALISATION, INTRIGUE), 3 regressed live (RÉGIME, ESPACE, TEMPORALITÉ), 1 tied (MODE). Always gold-check the specific drifted novels before concluding which version is "right" — don't default to trusting whichever is more recent. See [[project-task0-task1-status]] for the full table.
15. **A leaky model-selection bug (see #12) can live in more than one script that reuses the same pattern.** `train_chunk_classifier.py` (older, produces `resultats_chunk_classifier.csv`) has the identical best-of-3-picked-by-reported-score bug as `train_chunk_classifier_60novels.py` — found by directly reading the code, not assuming. Any script in this project with "try N sklearn classifiers, report the best" is a candidate for the same check before trusting its number in a hybrid recipe.
